# B1: authenticated GitHub approval comments

Status: **proposed design for owner review; no B1 runtime implementation is included**.

Date: 2026-11-03. Governing issue: [#3](https://github.com/tomazb/multi-agent-software-engineer/issues/3).

Implementation baseline: `adad3664ba4d536547f857328e610426548d03c4`.

The decisions below are the proposed bounded B1 design. Descriptions of existing behavior are tied to the inspected baseline. Earlier approved programme constraints are retained; this document does not claim that a prior conversation approved these detailed implementation choices. Owner approval of this specification precedes its implementation plan.

## 1. Purpose and delivery boundary

Allow an authorized GitHub user to approve the exact brainstorm or design artifact of an existing MASWE run through a PR conversation comment. MASWE commits that approval through its deterministic core, with attributable evidence and replay-safe outcomes.

B1 completes only the authenticated approval tranche of #3. The order remains B1 approvals, B2 branch/PR publication, B3 human-approved review resolution, then B4 Actions/artifact ingestion. Multi-harness runtime implementation and the distributed control plane retain their existing entry gates.

The smallest supported pilot is an **isolated managed-worktree run** (`run.config.policy.useIsolatedWorktree === true`, with a checkpointed `run.workspace.worktreePath`) already associated with an open, same-repository PR through the existing authenticated Phase A association flow. B1 neither creates an association from a command nor selects a run by topic, repository name, or model judgment. The command's run ID must match the existing numeric-repository/PR association.

**Pilot setup and workspace boundary:**

- **Managed worktrees only (`operator-checkout` out of scope for remote B1):** In `operator-checkout` mode (`run.config.policy.useIsolatedWorktree === false`), read-only role enforcement fingerprints the operator checkout's `.maswe/` tree, so a webhook-worker write under `.maswe/github/` that overlaps the read-only fingerprint interval causes a `policy-read-only-workspace-mutation` failure during continuation (pre-existing Phase A `.maswe/github/` writes in `operator-checkout` mode remain out of scope). Isolated managed worktrees fingerprint their own worktree checkout, which does not contain `.maswe/github/`. Fresh remote B1 approvals therefore require `run.config.policy.useIsolatedWorktree === true`, a checkpointed `run.workspace.worktreePath`, and existing managed-worktree ownership, branch (`maswe/<run-id>`), and HEAD checks. Runs with `run.config.policy.useIsolatedWorktree === false` are rejected definitively (`unsupported-workspace-mode`), and `maswe status` suppresses the remote command for them; runs with `useIsolatedWorktree === true` whose expected `worktreePath` checkpoint or workspace evidence is missing or damaged are treated as unresolved (damaged authority). Unassociated runs and `operator-checkout` runs continue to use the local `maswe approve` command without weakening the read-only workspace policy. B1 does not stop `.maswe/github/` writes for an `operator-checkout` run sharing the repository: the definitive `unsupported-workspace-mode` rejection receipt and every subscribed `issue_comment` inbox record still land under `.maswe/github/`, which the read-only fingerprint hashes. These writes fail closed and belong to the same class as the pre-existing Phase A writes, but subscribing to `issue_comment` raises their frequency.
- **Seeded same-repository PR setup prior to B2:** A new run started from the same commit as the PR target base has no diff to open a PR against. Standalone B1 pilot operation before B2 therefore starts an isolated managed-worktree run from a clean local feature commit that already differs from the intended PR target base. Bootstrap creates `maswe/<run-id>` at that exact commit. The operator publishes that exact branch tip (without moving the managed HEAD) and opens a same-repository PR to the intended target base while the run exists. Because Phase A will not re-associate by replaying an already-consumed `pull_request.opened` delivery, if the PR was opened before the run existed the operator must trigger a fresh supported Phase A PR event (convert the PR to draft and mark it `ready_for_review`, without pushing) after the run exists and verify association before posting an approval command. There is no `github-associate` CLI. B2 supplies deterministic branch/PR publication for ordinary new requests starting at the target base; B1 does not promise a complete new-request-to-new-PR workflow.

### Success outcome

An accepted remote approval atomically records its gate transition and receipt, moving:

| Gate | Required state | Existing event | Resulting state |
|---|---|---|---|
| `brainstorm` | `WAITING_FOR_BRAINSTORM_APPROVAL` | `APPROVE_BRAINSTORM` | `DESIGNING` |
| `design` | `WAITING_FOR_DESIGN_APPROVAL` | `APPROVE_DESIGN` | `BUILDING` |

The webhook worker does not invoke a model or execute the newly authorized phase. The operator subsequently runs `maswe run <run-id>` through the existing CLI. This keeps approval application and long-running execution separate without adding a continuation queue. The existing local `maswe approve <run-id> <gate>` retains its approve-and-run behavior through a wrapper around the same commit operation.

## 2. Baseline observations

The current [approval method](https://github.com/tomazb/multi-agent-software-engineer/blob/adad3664ba4d536547f857328e610426548d03c4/src/orchestrator.ts#L904-L913) sets an approval Boolean, calls `applyEvent`, and immediately calls `runUntilBlocked`. It accepts no artifact digest or GitHub actor proof. There are no separate `approveBrainstorm` or `approveDesign` methods.

The current [event types](https://github.com/tomazb/multi-agent-software-engineer/blob/adad3664ba4d536547f857328e610426548d03c4/src/github/types.ts) and normalizer do not admit `issue_comment`. The [durable worker](https://github.com/tomazb/multi-agent-software-engineer/blob/adad3664ba4d536547f857328e610426548d03c4/src/github/webhook-worker.ts) retries unsettled dispatch and completion failures. Delivery tombstones identify consumed deliveries, but are not stable comment-operation receipts across distinct delivery IDs.

`RunStore.applyEvent` saves the approval fields, state, and event in one version-checked durable `run.json` replacement. Because `writeDurableAtomic` renames the synced temporary file before calling `syncDurableDirectory`, its [outcome-unknown handling](https://github.com/tomazb/multi-agent-software-engineer/blob/adad3664ba4d536547f857328e610426548d03c4/src/store.ts#L602-L614) can read back the renamed `run.json` while parent-directory durability failed. A rejected promise therefore does not establish absence, and pathname visibility alone does not certify crash durability. Additionally, `requireOrdinaryRunNamespace` / `FileRunStore.readRunFile` and `withRunMutationFence` fold missing `.maswe`, missing `.maswe/runs`, and a missing run directory or missing `run.json` into `ENOENT`, so `FileRunStore.load` alone does not prove whole-run absence.

The current `FileRunStore.readArtifact` verifies confined paths and file size, but reads through `readBoundedOrdinaryFile`'s permissive UTF-8 string decoding (`Buffer.toString("utf8")`) before computing `SHA-256`. Corrupted raw bytes that decode to identical replacement text can pass the current reader despite a different raw-byte digest; B1 must tighten `FileRunStore.readArtifact` (across all roles) to hash bounded raw bytes and enforce fatal UTF-8 decoding with `ignoreBOM: true` before accepting an artifact. The [association mutation helper](https://github.com/tomazb/multi-agent-software-engineer/blob/adad3664ba4d536547f857328e610426548d03c4/src/github/association-mutation.ts) permits only `github`/`evidence` changes and protects event history; it cannot be used to commit or compensate an approval transition.

## 3. Approaches and selected direction

| Approach | Tradeoff | Disposition |
|---|---|---|
| Explicit PR comment with run, gate, and digest | Exact target is visible and can be checked through the existing PR association | Selected for this proposed B1 design, following the agreed comment-first direction |
| Approval labels | A label alone does not identify an immutable artifact or distinguish repeated application to newer work; a separate binding contract would be needed | Deferred |
| General issue/chat intake with an attention service | Supports new-work creation and multi-channel conversation, but needs additional authority, lifecycle, and persistence contracts | Separate future design |

The design adds a narrow comment-operation receipt store using existing durable-file and ownership-journal primitives. A successful approval receipt is also part of the authoritative run event. This is required because delivery-ID deduplication and success-only run events cannot preserve a finalized rejection/no-change outcome when the same comment arrives under another delivery ID. A generic outbox, scheduler, or new workflow state is unnecessary for B1.

## 4. Explicit enablement and permissions

Add the optional `githubApp.approvalComments` configuration:

```json
{
  "enabled": false,
  "commandPrefix": "/maswe",
  "allowedActorIds": [1279460]
}
```

The numeric ID is illustrative, not a default authorization grant. Omission means disabled. `allowedActorIds` is optional: omitted permits accounts satisfying the repository permission rule; an empty list permits nobody; a supplied list further restricts eligible numeric user IDs. The mandatory repository permission rule remains `write` or `admin`. No organization membership lookup or custom-role-name interpretation is introduced.

Validate the object as a closed schema, all IDs as unique positive safe integers, and `commandPrefix` as one ASCII slash token matching `^/[a-z][a-z0-9-]{0,31}$`. The prefix is a literal parser token, never a regular expression or shell fragment supplied by configuration. Prefix and parser bounds are fixed pilot choices, not performance findings.

Both the effective listener configuration and the immutable run configuration snapshot must explicitly authorize the operation; a broader live listener configuration can never widen the run snapshot, and Phase A's remote/branch association path does not substitute for run-level opt-in. The effective policy requires **all** of the following across both configurations:

1. `githubApp.enabled === true` and `githubApp.readOnlyChecks === true` in both listener and run configurations.
2. `githubApp.allowedRepositoryIds` in both configurations contains the exact numeric `repositoryId` (names in `allowedRepositories` grant nothing).
3. `githubApp.approvalComments?.enabled === true` in both configurations.
4. `githubApp.approvalComments.commandPrefix` matches identically in both configurations.
5. Listener `allowedActorIds` and run `allowedActorIds` are each evaluated independently (the verified numeric actor ID must satisfy both configurations' rules, where omission permits any account meeting the repository permission floor and `[]` permits nobody), in addition to the mandatory live `write`/`admin` repository permission.

Enforce in closed configuration parsing and validation (`normalizeGitHubAppConfig`, `assertGitHubAppConfig`, and `schemas/config.schema.json`) that `githubApp.approvalComments.enabled === true` is rejected unless `githubApp.enabled === true` and `githubApp.allowedRepositoryIds` contains at least one valid positive safe integer. Historical runs with no `githubApp` or no `approvalComments` opt-in stay disabled; B1 adds no mutation of historical configuration snapshots. Normal configuration restart/loading behavior remains in effect; this design adds no hot-reload service.

`githubApp.readOnlyChecks` stays `true`. It continues to limit GitHub resource mutations to the existing Phase A check behavior. The separately enabled B1 operation mutates local MASWE approval state. Documentation and operator output must make that distinction explicit; a historical Phase A configuration alone does not enable remote approvals.

### App registration versus narrowed REST tokens

- GitHub documents **Issues: read** as necessary to subscribe an App to `issue_comment`, including PR conversation comments. Enabling B1 therefore requires an explicit App/installation permission and event-subscription change.
- Reading the live comment accepts Issues: read or Pull requests: read. Reading a collaborator's effective repository permission requires Metadata: read.
- The existing ID-scoped `pull-request-read` token purpose already carries Metadata: read and Pull requests: read and can serve those REST reads. Do not broaden its minted permissions or add Issues/Contents/Pull requests write authority.
- Existing repository allowlisting remains numeric-ID based. Owner/name is current routing metadata only.

These distinctions follow GitHub's [webhook documentation](https://docs.github.com/en/webhooks/webhook-events-and-payloads#issue_comment), [comment read API](https://docs.github.com/en/rest/issues/comments#get-an-issue-comment), and [repository permission API](https://docs.github.com/en/rest/collaborators/collaborators#get-repository-permissions-for-a-user). Live installation qualification remains implementation validation, not evidence supplied by this design.

## 5. Command and ingress contract

Accepted command form, using the configured prefix:

```text
/maswe approve <brainstorm|design> <run-id> <run-version> <sha256>
```

Accept exactly one command line with single ASCII spaces and, optionally, one final LF or CRLF. Reject leading/trailing prose, Markdown quoting/fences, mentions, multiple commands, abbreviations, extra fields, uppercase/shortened digests, Unicode lookalikes, and path-like run IDs. Reuse `assertSafeRunId` and the existing safe ID contract. `run-version` is the displayed `RunRecord.version`, encoded as a positive safe decimal integer without leading zeros. SHA-256 is exactly 64 lowercase hexadecimal characters. Bound the complete command to 512 UTF-8 bytes; ordinary comments are not retained as command text.

The requested version is immutable input, never replaced by the newest version on retry. Every [run save](https://github.com/tomazb/multi-agent-software-engineer/blob/adad3664ba4d536547f857328e610426548d03c4/src/store.ts#L893-L908), including artifact publication and association changes, increments that version. It therefore binds the displayed artifact attempt and recorded PR/workspace context without a new persisted approval-request lifecycle. A benign run/name reconciliation can make a command stale; this conservative pilot tradeoff requires a refreshed status and a new comment. Exact historical receipt lookup precedes the version check, so an approval's own save does not defeat replay.

Only a signed `issue_comment.created` on a PR conversation is eligible. Ordinary issue comments, inline review comments, reactions, labels, edits, and deletions cannot grant B1 approval. An edited/deleted approval comment does not revoke an already committed approval; stopping work continues through existing operator controls. Before application, an edit or deletion makes the original request ineligible or unresolved as described below. The operator posts a new comment for a corrected command.

Extend closed normalized-event and durable-inbox validation together (closed-field rejection applies to normalized and persisted records only, so unrelated provider extension fields in raw GitHub payloads do not break valid webhooks). Retain only bounded typed fields needed for the command and its provenance: delivery identity/body digest, repository and installation IDs, PR number, comment ID, numeric sender/author IDs and account types, `performedViaGitHubApp` boolean provenance derived from `comment.performed_via_github_app`, routing login, comment timestamps, parsed command tuple including prefix and requested run version, and SHA-256 of the exact comment body. Existing raw-byte signature verification and body-size/UTF-8 validation remain before normalization. For a recognized PR command candidate on `issue_comment.created`, validate `comment.performed_via_github_app` strictly: `null` records `performedViaGitHubApp: false`; a plain object with a positive safe integer `id` records `performedViaGitHubApp: true`; missing or malformed shapes fail closed as HTTP `400` before enqueue. Ordinary non-candidate `issue_comment.created` comments remain unsupported (`200`), never `400`.

Recognize this bounded candidate grammar independently of the configured prefix, feature flag, allowlist, and current run eligibility. Syntactically valid candidates with a disabled feature, mismatched prefix, or ineligible actor reach the semantic receipt path and receive a durable rejection under the existing Phase A retention and operator-monitoring contract (Section 8). Otherwise a delivery-only drop could allow the same comment to gain an effect under a later configuration and different delivery ID. Ordinary non-candidate prose stays unsupported and is not retained as command text.

`comment.user` and `sender` must identify the same non-placeholder `User` account for a created command, **and** `comment.performed_via_github_app` must be `null` (not attributed to any GitHub App). An App/Bot account, an App user-to-server attributed comment (`performed_via_github_app !== null` even when `user.type === "User"`), an absent/placeholder account, or an ambiguous actor is not eligible and receives a definitive rejection without authority increase. GitHub account authentication remains the trust boundary: `User` with `performed_via_github_app === null` excludes GitHub App attribution (subject to live App qualification in B1-22) but does not distinguish direct browser input from a user's own PAT/OAuth token. Tokens, raw webhook bodies, unrelated comments, and raw model output must not enter approval receipts.

Capture the originating body digest before redaction and compare it with the digest of the authenticated live comment body. A material body change is detected even if the provider timestamp did not change. The body digest is provenance, not a bearer capability: possessing the digest or run ID grants no authority.

## 6. Application checks

For an unresolved operation, use the existing canonical-repository and association paths, then perform fresh authenticated reads within the application ownership boundary:

1. Confirm active B1 opt-in and numeric repository allowlisting across both listener and run configurations (Section 4), installation scope, and the ordinary non-suspended association. Both association index and `run.github` must identify the same installation/repository/PR/run tuple.
2. Require the command run ID to equal that existing association. Do not call candidate matching to create/rebind an association from approval text. Reject legacy ID-less and conflicting bindings through existing identity handling.
3. Read the current open PR using a deterministically built API route. Verify stable base-repository identity, PR number, head branch, and base/head SHAs against both `run.github` and the association index. A B1-specific observation must also require numeric `head.repo.id` equal to the base repository ID. The current [Phase A PR snapshot](https://github.com/tomazb/multi-agent-software-engineer/blob/adad3664ba4d536547f857328e610426548d03c4/src/github/pull-request.ts#L7-L21) intentionally does not read `head.repo`; preserve its existing fork support outside B1. A head/base change is stale approval context, not permission to replace workspace or evidence. Existing authenticated PR-event reconciliation remains separate.
   - **Stale-base pilot boundary, refresh runbook, and prerequisite:** Phase A ignores `pull_request.edited` (base-only retargets) and `maswe github-publish-checks` preserves the previously stored `baseSha`. After a base-only PR retarget, B1 rejects approval commands against the stale stored `baseSha`. To refresh manually, convert the PR to draft (`converted_to_draft`, ignored) and mark it ready for review (`ready_for_review`, ingested) without pushing — do not push (`synchronize` moves PR HEAD away from managed HEAD and guarantees step 6 rejection) and do not close/reopen (closing suspends the association as `pull-request-closed` until a `reopened` event recovers it; the draft→`ready_for_review` route avoids that suspension). Refreshing bumps `RunRecord.version`, so verify the updated base and version in `maswe status` and post a new approval command. Before pilot enablement, update `handlePullRequestEvent` (`src/github/adapter.ts`, excluding the unpersisted synthetic check-publication path and leaving `publishChecksForRun` untouched) to persist `snapshot.baseSha` from the already-fetched live PR snapshot rather than stale `event.baseSha` — or prove in `B1-22` that `ready_for_review` payloads always carry the drifted live `base.sha`. Because Phase A persists `baseSha` and not `baseRef`, the B1 pilot checks `baseSha` equality only; retargeting between two base branches pointing to the exact same commit SHA is undetected unless `baseRef` persistence is separately approved.
4. Read the comment by numeric ID from the reconciled repository. Verify its returned ID, containing issue/PR, numeric author ID/type, `performed_via_github_app` provenance, created/updated timestamps, and exact body digest against the admitted event. On live REST reads, **only explicit `null` passes** for `performed_via_github_app`: a well-formed non-null integration object is a definitive App-attribution rejection (and contradicts a creation event claiming `null`), whereas an omitted (`undefined`) or malformed `performed_via_github_app` field is unresolved/retryable (never defaulted to `null`). Treat URLs returned by GitHub as data to validate; never execute a payload-provided URL or shell command.
5. Query current repository permission for the freshly fetched author's login. Verify the response's numeric user ID matches the admitted actor. Only base `write`/`admin` qualifies; GitHub maps maintain to write and triage to read. `author_association`, display names, `role_name`, PR ownership, and review prose are insufficient.
6. Reload the authoritative run after lock acquisition. Require its version to equal the command's requested version, no supersession, matching active association, the full listener-and-run configuration intersection (Section 4), and the exact waiting gate. Enforce the managed-worktree pilot boundary: a run with `run.config.policy.useIsolatedWorktree === false` is rejected definitively (`unsupported-workspace-mode`); a run with `run.config.policy.useIsolatedWorktree === true` requires a checkpointed `run.workspace.worktreePath` and successful existing managed-worktree ownership, branch (`maswe/<run-id>`), and HEAD checks near commit (missing or damaged expected worktree checkpoint/evidence is unresolved, not `unsupported-workspace-mode`). Compare the verified workspace context with the PR head branch/SHA, preserving the applicable existing dirty-workspace/content policy rather than introducing a blanket clean-tree rule. `workspace.baseSha` is the [operator source HEAD captured at bootstrap](https://github.com/tomazb/multi-agent-software-engineer/blob/adad3664ba4d536547f857328e610426548d03c4/src/workspace-bootstrap.ts#L57-L69), while `run.github.baseSha` is the PR target-branch base: they are distinct facts and need not be equal. Select the artifact deterministically from the gate: `02-brainstorm.md` or `03-specification-and-design.md`.
7. Resolve the current immutable artifact reference and verify its **exact raw bytes** before decoding: read bounded raw `Buffer` bytes through a dedicated raw-byte reader (preserving `O_NOFOLLOW`, path confinement, before/after identity stability, and `MAX_AUTHORITATIVE_FILE_BYTES`, while keeping the existing string-returning `readBoundedOrdinaryFile` unchanged for JSON callers), compute `SHA-256` directly over those raw bytes, require exact equality with both the persisted `ArtifactReference.sha256` and the command's requested `<sha256>`, and decode with `new TextDecoder("utf-8", { fatal: true, ignoreBOM: true })` so valid BOM-bearing artifacts return byte-identical text to current consumers. Reject any raw-byte digest mismatch or invalid UTF-8 definitively (even when lossy decoding would produce identical characters); treat unavailable or unreadable artifact I/O as unresolved/retryable. This `FileRunStore.readArtifact` tightening applies across all roles. Record logical name, immutable attempt, and digest. No command-selected file path is admitted.
8. Apply the public commit-only core operation using the command's expected run version, artifact identity, context, and validated bounded source provenance. A version conflict discards the prepared authorization observation. Reacquire ownership and check for an exact committed receipt first; if none exists and the current version differs, finalize a stale rejection. Never rebase the request onto a newer version. Any otherwise eligible retry rechecks external facts.

**Definitive vs. retryable classification:**

- **Definitive outcomes (settle immediately into a final semantic receipt and complete the delivery):** `applied`; and definitive rejections — disabled policy/missing opt-in/mismatched prefix, `unsupported-workspace-mode` (`useIsolatedWorktree === false`), ineligible actor (`Bot`/placeholder/`performed_via_github_app !== null`/`sender !== author`/user-ID mismatch), insufficient live repository permission (`read`/`none`/triage) or actor failing either `allowedActorIds` rule, missing/suspended/fork/conflicting/legacy association, proven `no-such-run` (Section 8 step 3), wrong waiting gate, stale `run-version` (including any losing distinct competing approval comment), stale PR head/base/branch, live comment body/timestamp/PR mismatch, and proven raw-byte artifact digest mismatch or invalid UTF-8. A request-identity conflict under an existing semantic key is also definitive, but it never creates or modifies a semantic receipt; its outcome lives only in the inbox completion (Section 8).
- **Retryable / ambiguous outcomes (never invent a final acceptance or rejection; governed by the finite B1 retry policy in Section 8):** GitHub rate limits, timeouts, transient 5xx/transport failures, malformed GitHub API responses, missing/malformed live `performed_via_github_app`, `404` responses on live comment/PR/permission lookups (kept retryable in B1 to avoid permanently rejecting valid approvals on read-replica lag or unqualified token nuances), unavailable/damaged/unreadable run, expected managed-worktree checkpoint, artifact I/O, or receipt files, failed directory-sync durability reconfirmation, uncertain atomic writes, and lock contention.

Receipt replay, described next, is checked before considering a new transition.

Remote permission and PR state can change after an API observation. B1 promises fresh execution-time observation and local version/ownership checks; it does not claim an atomic transaction spanning GitHub authorization and the local filesystem. Store observation times, and do not reuse authorization across a released/reacquired lock or retry.

## 7. Core ownership and commit boundary

Introduce a public commit-only approval operation in `src/orchestrator.ts`. Its exact TypeScript method name is an implementation choice; its contract is not:

- Accept expected run/gate/artifact/context identity and a validated, typed provenance record.
- Establish/reuse the existing run target mutation fence without recursive acquisition; reload the run and reassert the local preconditions within it.
- Check for an exact prior accepted operation before rejecting a now-advanced state.
- Commit the approval Boolean, existing transition, and typed approval receipt in one `RunStore.applyEvent`/save CAS.
- Return a typed applied/already-applied/rejected result without starting the next role.

The adapter owns authenticated GitHub reads and routing. The core owns artifact/state/transition validation and durable approval acceptance. Neither a webhook handler nor an LLM writes approval fields directly. A typed argument alone is not proof of remote authorization: the only production GitHub entry path must perform the checks above, and this internal core method is not exposed as an unauthenticated RPC.

The local CLI wrapper supplies local-user provenance and the current verified artifact, calls the same commit-only operation, then preserves its existing `runUntilBlocked` behavior. Explicitly test this reconciliation: local approval now uses the same verified artifact commit boundary, while remote approval stops at the next phase state.

### Lock ordering

Use one `approval-operation` ownership journal per semantic operation as the outermost B1 lock. Inside it, preserve the existing order:

1. Repository-identity entry/reconciliation fence, released before longer PR work.
2. PR publication fence keyed by numeric repository ID and PR number.
3. PR association-identity fence for the same tuple.
4. Run target mutation fence.
5. Global association transaction only for a bounded snapshot/check if needed, then the run store's data CAS at commit.

No existing path acquires an approval-operation lock while holding an inner lock. The implementation must reuse/extract the existing fence helpers so no callback reacquires a held journal. Do not hold the global association transaction during network requests or model execution. Re-read the index and run before approval commit, and serialize/reject changes through the same existing ownership and CAS boundaries used by association/recovery work.

Do not put approval writes inside `saveGitHubAssociationMutation` or register them for its rollback. An accepted approval event is monotone historical evidence; an unrelated association settlement failure cannot undo it. The local CLI path and remote path must converge on the same run-fenced core operation; cancellation/supersession or another run writer still wins or loses by the existing version check, never by overwriting a newer record.

## 8. Semantic receipts and recovery

### Two identities

`deliveryId` identifies an authenticated webhook delivery. A semantic approval operation is keyed by the pair `(numeric repository ID, numeric comment ID)`, independent of delivery ID, mutable repository name, and later installation/name changes.

Define its stable key as SHA-256 of the UTF-8 JSON array `["github-approval-comment",1,repositoryId,commentId]`. Validate each record's embedded tuple against the filename/key. Compare an immutable request identity containing originating installation, PR, numeric actor ID, actor account type, sender/author identity, `performedViaGitHubApp`, created/updated timestamps, command prefix/run/requested-version/gate/artifact digest, and exact comment-body digest. Whole webhook body digests remain per-delivery provenance; they do not redefine semantic identity across delivery IDs.

### Feature-specific operation record and retention boundary

Persist a closed, versioned record under `<githubRoot>/approval-comments/<key>.json`, using existing ordinary-file checks, a new B1-specific **64 KiB** per-record byte limit (distinct from the existing 1 MiB `MAX_AUTHORITATIVE_FILE_BYTES`), durable atomic writes, and the shared ownership-journal library with a distinct typed namespace (`approval-operation`). The record has only `pending` and `final` lifecycle states; these are receipt states, not new MASWE workflow states.

A pending record binds the immutable request and first delivery before application. A final record contains one outcome: `applied` (naming the run and exact `APPROVE_*` event/receipt that justifies it) or `rejected` with a bounded reason code. Losing distinct competing comments always target a now-stale `RunRecord.version` and settle as deterministic stale rejections; final semantic records do not define a separate `already-satisfied` outcome (the core commit operation in Section 7 retains its `already-applied` return for exact replay of the winning operation). Record actor, `performedViaGitHubApp` check status, policy observation identity, run/artifact/head context, and timestamps in bounded typed fields; never retain credential material. A rejection does not change workflow state.

Final records are immutable. A replay with identical request identity returns that final outcome; a different tuple/body/actor-provenance for the same key is a conflict and cannot overwrite the record. This rule also applies when an earlier rejection preceded association creation or a permission/configuration change.

An `APPROVE_*` event stores the authoritative successful receipt in the same run write as the gate transition. Its receipt includes schema version, semantic key/request identity digest, requested run version, source actor and delivery reference, approved artifact name/attempt/digest, evaluated association and separate PR/workspace base/head facts, and authorization observation. Extend durable event validation with this closed typed shape. Historical events remain readable but are never upgraded into remote approval receipts.

### Ordered protocol and unconditional durability reconfirmation

Route typed B1 candidates to this protocol before the adapter's ordinary unsupported-type and mutable repository-policy early exits; existing observe-only event kinds retain their behavior. Recovery of an earlier accepted effect requires the original authenticated bounded identity, not current permission, an active association, or a surviving managed worktree. Terminal cleanup may already have removed that worktree. This recovery branch only reports history; all fresh application remains subject to Section 6.

**Unconditional crash-durability reconfirmation:** Because `writeDurableAtomic` renames before calling `syncDurableDirectory`, observing a file by pathname never certifies that its parent directory entry is crash-durable. Always unconditionally reconfirm parent-directory durability via `syncDurableDirectory` and re-verify the exact canonical record before **any** pathname-visible record authorizes advancing to the next step:

- `run.json` receipts: through a dedicated `RunStore` durability-reconfirmation method under the run target fence (the adapter must not reach into `FileRunStore` internal paths);
- `pending` and `final` semantic operation records: under the `approval-operation` lock;
- inbox state records: under the existing `delivery` fence (acquired only after releasing application fences) before duplicate HTTP acknowledgement (`200`/`202`), before the shared `complete()` fast path returns `true` (hardening all deliveries, not B1 only), and before removing a queue marker after observing a `completed` or `retry-exhausted` record (including startup recovery).

If durability reconfirmation or exact verification fails, stop immediately and leave the operation unsettled and retryable.

1. Acquire the semantic operation lock and load any record.
   - If a `final` record exists: reject a conflicting request identity without modifying the record. For an identical request identity, unconditionally reconfirm parent-directory durability of `<githubRoot>/approval-comments/` before completing the delivery. For an `applied` outcome, reload and validate the referenced authoritative `APPROVE_*` receipt in the run record and unconditionally reconfirm durability of that run directory via `RunStore`; missing, corrupt, or contradictory run evidence is unresolved (unsettled/retryable), never permission to silently report success or reconstruct an approval.
   - If a `pending` record exists: reject a conflicting request identity without modifying the record, recording the conflict only in the inbox completion. For an identical request identity, unconditionally reconfirm parent-directory durability of `<githubRoot>/approval-comments/` and continue at step 3 without rewriting the record.
2. Persist the `pending` identity durably before changing run state. If that write is outcome-unknown, re-read the exact record and reconfirm parent-directory durability via `syncDurableDirectory` under the semantic operation lock before proceeding.
3. Probe run presence through a dedicated `RunStore` method returning `absent | present | unsettled` before acquiring any run fence (because `withRunMutationFence` and `requireOrdinaryRunNamespace` fold missing `.maswe`, missing `.maswe/runs`, and a missing run directory into `ENOENT`):
   - `FileRunStore` verifies `.maswe` and `.maswe/runs` exist as ordinary directories (missing store parents return `unsettled`) and inspects `.maswe/runs/<runId>` via `lstat`.
   - Only a direct `ENOENT` on `.maswe/runs/<runId>` beneath verified ordinary store parents returns `absent` and permits finalizing a `no-such-run` rejection without creating a run or run fence.
   - For an ordinary existing run directory (`present`), load and validate `run.json`; missing, corrupt, oversized, or inaccessible `run.json`, or a non-directory/symlink `.maswe/runs/<runId>`, returns `unsettled` (never finalize `no-such-run`).
   - For a readable existing run, acquire the run target fence and search its validated `APPROVE_*` receipts before ordinary live eligibility routing. If an exact committed receipt matches this operation, unconditionally reconfirm run-directory durability via `RunStore` under the run target fence, then settle the semantic operation record as `applied` even if workflow state has advanced or current authorization has since changed (this reports an earlier fact, not new authority). Release this recovery-only run fence before acquiring the full ordered application fences for any fresh effect.
4. If no committed receipt exists, perform fresh application checks (Section 6). A valid request commits one approval event/Boolean/state atomically. A definitive rejection/no-change result is finalized in the operation record without a gate transition.
5. Settle the semantic operation record from the committed run receipt (only after the run commit succeeded or its run-directory durability was reconfirmed). If that write fails or is outcome-unknown, keep the delivery retryable. Never compensate the committed run event.
6. Complete the inbox delivery only after the final semantic operation record is durably persisted and directory-synced (or reconfirmed). A bounded completion outcome/reference may be added to the existing inbox tombstone for inspection; it is not the semantic receipt authority.

On an ambiguous run save (`DurableAtomicWriteOutcomeUnknownError`), reload the authoritative run under the run target fence and validate the exact receipt. If present, unconditionally reconfirm run-directory durability via `RunStore` before reconciling and settling the completed approval; confirmed absence of the receipt (with an intact, readable prior `run.json`) permits a fully revalidated retry; an unreadable, ambiguous, or failed-sync result remains blocked/retryable. Never infer absence from a thrown save, never infer crash durability from pathname visibility alone, and never infer success from a Boolean.

### Bounded B1 retry policy and operator recovery

Unsettled B1 deliveries use a finite B1-only retry policy (Phase A deliveries keep their existing retry behavior):

- **Schedule and deadline:** Exponential backoff starts at `250 ms` and keeps doubling up to a **5-minute B1 backoff ceiling** within a **1-hour elapsed wall-clock deadline** (~22 attempts/hour vs ~127 at `30 s`, limiting installation REST quota impact while surviving transient rate limits, 5xx outages, and restarts). Initial `retryDeadlineAt = receivedAt + 1h` is persisted at first enqueue on the closed `InboxDeliveryRecord` (preserving original `record.receivedAt` and `event.receivedAt` intact so `validEvent` stays valid across restarts). Process downtime counts against the wall-clock deadline: a restart after `retryDeadlineAt` exhausts queued B1 deliveries without another attempt. Enforce the deadline uniformly at **every claim, lease reclaim, startup recovery, and worker retry** under the `delivery` fence.
- **Exhaustion disposition (owner-gated persisted-format addition):** Add closed status `retry-exhausted` to `InboxDeliveryStatus` (existing `awaiting-redelivery` is legacy-only and forbids retained event/digest fields; older binaries will reject `retry-exhausted` records). At deadline expiry, durably persist `retry-exhausted` (keeping the normalized event and `retryDeadlineAt`), reconfirm state-directory sync, remove the queue marker, preserve any `pending` semantic receipt intact, make **no change to the run** (preserving any already-committed approval), and write **no final semantic rejection**. **The durable `retry-exhausted` record is authoritative. Emit a best-effort sanitized diagnostic (`GITHUB_WEBHOOK_RETRY_EXHAUSTED`) when entering exhaustion.**
- **Operator recovery:** GitHub webhook redelivery reuses the original `X-GitHub-Delivery`. Only an authenticated exact-digest redelivery observing `retry-exhausted` resets `retryDeadlineAt` (`now + 1h`, preserving original `record.receivedAt` and `event.receivedAt`), durably transitions `retry-exhausted` → `queued` with its queue marker under the `delivery` fence, and returns HTTP `202`. Exact duplicates observing `queued` or `processing` preserve the active `retryDeadlineAt` without extending it; an exact completed duplicate returns `200` after durability confirmation; a conflicting event or body digest returns `409`. Note explicitly that the receiver cannot distinguish human-initiated redelivery from any other authenticated exact redelivery of an exhausted delivery.

Receipts must not be evicted or expired in a way that reactivates an old operation. B1 adds no numeric lifetime operation cap and introduces no automatic receipt GC: each record is bounded to 64 KiB, and receipts plus `approval-operation` journals fall under the existing Phase A retention and operator-monitoring contract in `docs/GITHUB_APP.md` (`## Capacity, retention, shutdown, and recovery`). Subscribing to `issue_comment` grows permanent `.maswe/github` state per signed `issue_comment` delivery (including issue comments, edits, deletes, and non-candidate PR comments); operators monitor bytes and inodes and stop ingress before filesystem exhaustion. Storage failure or malformed records produce explicit unsettled/operator-visible failure. Decommissioning/reset of a state namespace is an operator procedure outside replay-preserving B1 operation and discards rejection receipts.

### Failure matrix

| Interruption or race | Required result |
|---|---|
| Before pending intent is durable | No approval; retry admission under current facts (within 1-hour B1 retry window) |
| Pending intent exists, before core save | Revalidate and apply at most one matching transition |
| Core save landed after rename, directory sync failed (`outcome-unknown`) | Re-read exact run receipt under run fence and unconditionally reconfirm `syncDurableDirectory` via `RunStore`; settle only after sync succeeds, else stay unsettled/retryable |
| Core save landed and confirmed durable; operation settlement or inbox completion failed | Replay reconciles and returns the same approval; no second event or automatic execution |
| `complete()` fast path, duplicate HTTP ack, or marker removal observes visible inbox state after failed directory sync | Unconditionally reconfirm inbox state-directory sync under the `delivery` fence before returning `200`/`202` or unlinking queue marker |
| Final `applied` replay with missing/corrupt/contradictory run receipt | Unsettled/blocked; never silently report proven success or reconstruct authority |
| Final no-change/rejection, replay under a new delivery ID after state/permission changes | Original final outcome; no new authority |
| Same semantic key with different run, gate, body, or actor/provenance | Conflict; original record remains unchanged |
| Missing `.maswe/runs`, or existing `.maswe/runs/<runId>` with missing/corrupt `run.json` | Unsettled/blocked; never finalize `no-such-run` |
| Two comments or CLI/remote approval race | One matching gate transition; losing distinct comment fails stale `RunRecord.version` check as deterministic rejection; winning exact replay returns `applied` |
| Cancellation, supersession, association change, or artifact replacement races application | Ownership/CAS and fresh checks reject stale application |
| Persistent remote lookup uncertainty, unreadable receipt/run, or sync failure passes 1-hour `retryDeadlineAt` | Delivery enters `retry-exhausted` (queue marker removed after dir sync, evidence preserved, no run change, any committed approval preserved, best-effort sanitized diagnostic emitted); exact redelivery observing `retry-exhausted` establishes one new deadline and returns `202` |

## 9. Operator experience

Expose B1 decisions through the existing status/JSON and bounded local delivery diagnostics. An accepted result identifies the run, gate, immutable artifact, actor, receipt, resulting phase, and the existing `maswe run <run-id>` continuation command. It must say that approval was recorded and execution awaits that command. It must not report implementation or verification success.

The approval presentation is a projection of authoritative state, for example:

```text
Decision needed: approve design
Run: <run-id>, version <v>
Artifact: 03-specification-and-design.md, attempt <n>, SHA-256 <digest>
Context: repository <numeric-id>, PR <number>, head <sha>
Action: /maswe approve design <run-id> <v> <digest>
After acceptance: BUILDING; continue with maswe run <run-id>
```

Render only an action valid for the current state and verified artifact. A status view is advisory; application rechecks all authoritative preconditions. Do not silently fabricate retry eligibility from a terminal-state label; the independently scoped [#48](https://github.com/tomazb/multi-agent-software-engineer/issues/48) contract correction remains separate.

B1 sends no new GitHub replies/reactions and creates no dashboard, question lifecycle, notification queue, assignment/snooze state, or autonomous intake. Existing checks remain Phase A behavior. External communication features retain their later tranche scope.
